# 関連研究（本体未収録の実験的手法）

広聴AI の周辺で試されているが、**本体には収録していない**手法の紹介です。どれも個人の repo やデモとして存在し、成熟度は「動くものがあり、本人が結果を見て考え中」の段階です。本体に無い理由は「悪いから」ではなく、まだ効果の評価が済んでおらず、本体の構造（意見ごとの属性、分析モード、結果 JSON の契約）にどう載せるかが決まっていないからです。

このページの役割は 2 つです。

- 「同じトピックの中に賛否が混在する」「少数だが珍しい意見を拾いたい」という問いに対して、**何がどこで試されているか**を contributor が探し直さずに済むようにする
- 個人 repo は所有者の都合で消えたり動かなくなったりするので、**最終確認日**を添えて「いつ時点の情報か」を残す

ここに載っている手法を本体に入れる場合は、Web UI ではなく **CLI の任意ステップまたは分析モードから**入れます（[CLI クイックスタート](../user-guide/cli-quickstart.md)）。既定では無効にし、結果は既存の仕組み（`arguments[].attributes` の属性、または分析モードごとの結果 JSON）に載せます。Web UI に載せるかは、CLI で artifact を貯めて読み比べてから判断します。

## 共通の問題意識

2 手法はどちらも、2025-11〜12 の定例で tokoroten が述べた次の仮説から出ています。

> 対立を解決する、反対派をケアすることが政治家の仕事であると仮定したときに、現在の一つのトピック内に賛否が混在しているという状況はインサイトに繋がりにくい。

広聴AI の散布図は意味の近さでクラスタを作るので、「原発を増やすべき」と「原発を減らすべき」は同じクラスタに入ります。読者が「何が対立しているか」を知りたいとき、クラスタのラベルと代表意見だけでは賛否の構造が見えません。書籍『ブロードリスニング』13.4.3「賛否分離」はこれを「次に手を入れる場所」として挙げ、2 つのアプローチを示しています。

## センチメント次元の付与（sentiment-weighted UMAP） {#sentiment-dimension}

### 要点

1. 意見の抽出時に、LLM が各意見の賛否スコア（-1.0〜+1.0）を推定する
2. スコアに重み（weight）を掛けて埋め込みベクトルに 1 次元として連結し、そのうえで UMAP にかける
3. weight を上げるほど、同じトピック内で賛成と反対が離れて別クラスタになる。上げすぎるとトピック間の類似性が消え、「賛成の島」と「反対の島」だけになる

書籍では電力政策のパブリックコメント約 1,000 件で、weight = 0.75 のときに風力発電のクラスタが賛否で分かれた図が示されています。デモはこの weight をスライダーで連続的に動かせる形で、重みを変えたときに点が滑らかに移動するよう「連続性を保つためのトリック」が入っています。

### 所在

- デモ（自己完結 HTML、約 14 MB）: <https://sentiment-weighted-umap-animation.netlify.app/combined_interactive.html>
- コード（zip）: <https://sentiment-weighted-umap-animation.netlify.app/posinega_separation.zip>
- 本人の報告: 2025-11 の定例。「これ以上は政治家に使ってもらわないと分からない」が当時の評価

### 本体との関係

この手法は「賛否スコアを付ける」前段と「埋め込みに重みを掛ける」後段に分かれます。

- **前段（賛否スコア）**は、意見ごとに LLM で yes/no のラベルを付ける任意ステップ [`opinion_classification`](opinion-classification.md) と同じ「意見ごとの属性」の形に載ります。-1.0〜+1.0 のスコアを `arguments[].attributes` に入れれば、ビューアの属性フィルタで「賛成だけの地図」「反対だけの地図」を既存の散布図のまま見られます。これは Issue [#1158](https://github.com/digitaldemocracy2030/kouchou-ai/issues/1158) で CLI の任意ステップとして提案しています
- **後段（埋め込みへの重み付け）**は本体に入れていません。入れるなら `embedding` ステップの任意設定にし、同じコーパス・同じクラスタリング・同じラベリングで weight だけを変えた比較で「賛否で分かれたか」と「トピックの近さが壊れていないか」を同時に見てから判断します。色分けとフィルタで足りるなら、座標を変える必要はありません

## DivCon（Divide and Conciliate） {#divcon}

### 要点

埋め込みと UMAP を使いません。LLM の long context で次を順に行います。

1. トピック発見: 意見全体からトピックを抽出する
2. 意見分類: 各意見をトピックに割り当てる
3. 対立軸の発見: トピックごとに、意見が割れている軸を見つける
4. アンカー生成: 各対立軸の両極を代表する意見を作る
5. スコアリング: 各意見を対立軸上の位置で 6 段階（1 = 左極〜6 = 右極）に採点する

出力は、対立軸ごとに左右の意見を並べる「2 ペインビュー」と、フィルタ・検索できる「リストビュー」で、散布図は出ません。強硬な意見が両端に並ぶので、「どこで割れているか」を読むためのビューです。

2025-12 の定例では「対立を扱う場合に embedding を介するのは筋が通らないので、long context で直接やるのがよい。Jigsaw Sensemaker が long context で 2 階層ツリーを作ってから一次データを分類するのと同じ型で、long context で対立構造を作ってから分類する」と整理されました。

### 所在

- repo: <https://github.com/tokoroten/divcon>（MIT License、最終 push 2025-11-20）。`experiments/divcon_analysis.py` が OpenAI API を直接呼ぶ単体スクリプトで、入力は `id, comment` の CSV
- デモ（エネルギー政策パブリックコメント 1,024 件、トピック 6、対立軸 20）: [2 ペインビュー](https://tokoroten.github.io/divcon/) / [リストビュー](https://tokoroten.github.io/divcon/list.html)
- 自治体の意見データでの試行は 2025-12 の定例で報告。結果の評価は公表されていません

### 本体との関係

本体の `analysis_mode=llm_grouping`（LLM 直接グルーピング。意見のサンプルから LLM がグループを見つけ、全件を割り当てる方式）と同じ「group-first」の分析ですが、対立軸の発見・アンカー生成・スコアリングに当たる処理は本体にありません（2026-10-29 時点）。

本体に入れるなら、tokoroten の repo を移植するのではなく、`llm_grouping` と同じステップ構造で書き直し、結果 JSON に「対立軸」「アンカー」「各意見のスコア」をどう持たせるかの契約を先に決めます。散布図を出さない分析なので、対立ビューはその契約を要求する可視化として後から足します。評価には、賛否が実際に混ざっているパブリックコメントのデータが要ります。

## farbrain {#farbrain}

### 要点

分析手法ではなく、ブレインストーミングのゲーミフィケーションツールです。参加者の投稿を LLM が整形し、多言語の sentence-transformers で埋め込み、既存の投稿集合からの距離で「新規性スコア」を付けて競わせます。可視化は UMAP → k-means → 凸包 → LLM によるクラスタ表札で、広聴AI と同じ部品をリアルタイム・多人数で回しています。

### 所在

- repo: <https://github.com/tokoroten/farbrain>（最終 push 2025-12-14）
- 解説記事: [FarBrain：俺が考えた最強のブレストソフトを作った話](https://note.com/tokoroten_jp/n/n8c2b2e6fe35b)

### 本体との関係

広聴AI に持ち込める要素は 2 つです。

- **新規性スコア**: 既存の埋め込み集合からの遠さを意見ごとの属性にすると、「少数だが珍しい意見」の候補に印を付けられます。farbrain は平均コサイン距離や Isolation Forest など複数の変換を持ちます。広聴AI では Issue [#1158](https://github.com/digitaldemocracy2030/kouchou-ai/issues/1158) で、`embedding` ステップの後に LLM なしで計算する任意ステップとして提案しています。スコアは候補を絞るだけで、「重要」かどうかはプロンプトに言語化する分析者の責務です
- **自分の投稿のハイライト**: 意見を投稿した人が「自分がどのクラスタにいるか」を見つけられる表示。未着手です
