# 周辺の研究・実験（本体未収録）

広聴AI の周りで行われている研究・実験のうち、**まだ本体に取り込まれていないもの**の紹介です。どれも個人の repo やデモとして動いていて、広聴AI と同じ部品を使ったり、広聴AI の出力を読んだりして、本体とは別の見方や手法を試しています。

本体に入っていないのは「質が低いから」ではありません。本体に入れるには、効果を比べて確かめることと、本体の構造（意見ごとの属性、分析モード、結果 JSON の契約）にどう載せるかを決めることが要り、それには時間がかかります。本体の外なら、その手続きを待たずに新しい見方を試し、使ってみた結果から何を本体に持ち込むかを考えられます。

## 本体の外での試みを歓迎します

広聴AI の出力を使って新しい分析や可視化を試すのに、本体を変える必要はありません。

- 可視化なら、公開用の結果 [`public_result.json`](public-result.md) を読めば描けます。意見ごとの属性（[`arguments[].attributes`](public-result.md)）は自由形式なので、自分で足したスコアやラベルもそこに入れて読めます
- 分析手法なら、[CLI](../user-guide/cli-quickstart.md) の出力（`outputs/<dataset>/`）を入力にした単体のスクリプトから始められます
- 自分の repo とデモで公開し、このページに 1 行足してください。本体に入れるかどうかは、使われ方を見てから CLI の任意ステップや分析モードとして検討します（下の「本体に入れるとき」）

このページの役割は 2 つです。

- 「同じトピックの中に賛否が混在する」「少数だが珍しい意見を拾いたい」「散布図以外の形で見たい」といった問いに対して、**何がどこで試されているか**を探し直さずに済むようにする
- 個人 repo は所有者の都合で消えたり動かなくなったりするので、**最終確認日**を添えて「いつ時点の情報か」を残す

## 賛否分離の 2 手法に共通の問題意識

センチメント次元の付与と DivCon は、どちらも 2025-11〜12 の定例で tokoroten が述べた次の仮説から出ています。

> 対立を解決する、反対派をケアすることが政治家の仕事であると仮定したときに、現在の一つのトピック内に賛否が混在しているという状況はインサイトに繋がりにくい。

広聴AI の散布図は意味の近さでクラスタを作るので、「原発を増やすべき」と「原発を減らすべき」は同じクラスタに入ります。読者が「何が対立しているか」を知りたいとき、クラスタのラベルと代表意見だけでは賛否の構造が見えません。書籍『ブロードリスニング』13.4.3「賛否分離」はこれを「次に手を入れる場所」として挙げ、2 つのアプローチを示しています。

## センチメント次元の付与（sentiment-weighted UMAP） {#sentiment-dimension}

### 要点

1. 意見の抽出時に、LLM が各意見の賛否スコア（-1.0〜+1.0）を推定する
2. スコアに重み（weight）を掛けて埋め込みベクトルに 1 次元として連結し、そのうえで UMAP にかける
3. weight を上げるほど、同じトピック内で賛成と反対が離れて別クラスタになる。上げすぎるとトピック間の類似性が消え、「賛成の島」と「反対の島」だけになる

書籍では電力政策のパブリックコメント約 1,000 件で、weight = 0.75 のときに風力発電のクラスタが賛否で分かれた図が示されています。デモはこの weight をスライダーで連続的に動かせる形で、重みを変えたときに点が滑らかに移動するよう「連続性を保つためのトリック」が入っています。

### 所在

- デモ（自己完結 HTML、約 14 MB）: <https://sentiment-weighted-umap-animation.netlify.app/combined_interactive.html>
- コード（zip）: <https://sentiment-weighted-umap-animation.netlify.app/posinega_separation.zip>
- 本人の報告: 2025-11 の定例。「これ以上は政治家に使ってもらわないと分からない」が当時の評価
- 広聴AI の出力に当てた版: [可視化カタログ](#visualization-catalog)の「賛否スライダー」

### 本体との関係

この手法は「賛否スコアを付ける」前段と「埋め込みに重みを掛ける」後段に分かれます。

- **前段（賛否スコア）**は、本体の任意ステップ [`opinion_stance`](opinion-scores.md) として入りました。`arguments[].attributes.stance_score` に数値で入るので、ビューアの属性フィルタで「賛成だけの地図」「反対だけの地図」を今の散布図のまま見られます
- **後段（埋め込みへの重み付け）**は本体に入れていません。入れるなら `embedding` ステップの任意設定にし、同じコーパス・同じクラスタリング・同じラベリングで weight だけを変えた比較で「賛否で分かれたか」と「トピックの近さが壊れていないか」を同時に見てから判断します。色分けとフィルタで足りるなら、座標を変える必要はありません

## DivCon（Divide and Conciliate） {#divcon}

### 要点

埋め込みと UMAP を使いません。LLM の long context で次を順に行います。

1. トピック発見: 意見全体からトピックを抽出する
2. 意見分類: 各意見をトピックに割り当てる
3. 対立軸の発見: トピックごとに、意見が割れている軸を見つける
4. アンカー生成: 各対立軸の両極を代表する意見を作る
5. スコアリング: 各意見を対立軸上の位置で 6 段階（1 = 左極〜6 = 右極）に採点する

出力は、対立軸ごとに左右の意見を並べる「2 ペインビュー」と、フィルタ・検索できる「リストビュー」で、散布図は出ません。強硬な意見が両端に並ぶので、「どこで割れているか」を読むためのビューです。

2025-12 の定例では「対立を扱う場合に embedding を介するのは筋が通らないので、long context で直接やるのがよい。Jigsaw Sensemaker が long context で 2 階層ツリーを作ってから一次データを分類するのと同じ型で、long context で対立構造を作ってから分類する」と整理されました。

### 所在

- repo: <https://github.com/tokoroten/divcon>（MIT License、最終 push 2025-11-20）。`experiments/divcon_analysis.py` が OpenAI API を直接呼ぶ単体スクリプトで、入力は `id, comment` の CSV
- デモ（エネルギー政策パブリックコメント 1,024 件、トピック 6、対立軸 20）: [2 ペインビュー](https://tokoroten.github.io/divcon/) / [リストビュー](https://tokoroten.github.io/divcon/list.html)
- 自治体の意見データでの試行は 2025-12 の定例で報告
- 広聴AI の出力に当てた版: [可視化カタログ](#visualization-catalog)の「対立軸ビュー」

### 本体との関係

本体の `analysis_mode=llm_grouping`（LLM 直接グルーピング。意見のサンプルから LLM がグループを見つけ、全件を割り当てる方式）と同じ「group-first」の分析ですが、対立軸の発見・アンカー生成・スコアリングに当たる処理は本体にありません。

本体に入れるなら、tokoroten の repo を移植するのではなく、`llm_grouping` と同じステップ構造で書き直し、結果 JSON に「対立軸」「アンカー」「各意見のスコア」をどう持たせるかの契約を先に決めます。散布図を出さない分析なので、対立ビューはその契約を要求する可視化として後から足します。評価には、賛否が実際に混ざっているパブリックコメントのデータが要ります。

## farbrain {#farbrain}

### 要点

分析手法ではなく、ブレインストーミングのゲーミフィケーションツールです。参加者の投稿を LLM が整形し、多言語の sentence-transformers で埋め込み、既存の投稿集合からの距離で「新規性スコア」を付けて競わせます。可視化は UMAP → k-means → 凸包 → LLM によるクラスタ表札で、広聴AI と同じ部品をリアルタイム・多人数で回しています。

### 所在

- repo: <https://github.com/tokoroten/farbrain>（最終 push 2025-12-14）
- 解説記事: [FarBrain：俺が考えた最強のブレストソフトを作った話](https://note.com/tokoroten_jp/n/n8c2b2e6fe35b)

### 本体との関係

広聴AI に持ち込める要素は 2 つです。

- **新規性スコア**: 既存の埋め込み集合からの遠さを意見ごとの属性にする考え方は、本体の任意ステップ [`opinion_novelty`](opinion-scores.md) として入りました（LLM なし、`embedding` の後）。スコアは「少数だが珍しい意見」の候補を絞るだけで、「重要」かどうかは分析者が決めます
- **自分の投稿のハイライト**: 意見を投稿した人が「自分がどのクラスタにいるか」を見つけられる表示。本体には入っていません。可視化カタログの「自分の声を探す」が、本体外で近い見せ方を試しています

## 広聴AI 可視化カタログ {#visualization-catalog}

### 要点

広聴AI の公開用の結果 `public_result.json` を入力に、散布図以外の形で描く試作集です。本体の契約を変えずに描けるものを、本体の外で作って公開し、使われたものから本体に入れるかを判断する、という置き場として作られました。項目によっては `public_result.json` のほかに、カタログの repo のスクリプトで作る追加の入力が要ります（表の「入力」）。

| 名前 | 何を見せるか | 入力 | 状態（2026-11-11） |
|---|---|---|---|
| 意見マンダラート | 意見を 8 つずつに割った木を、中心＋周り 8 マスで降りていく | `public_result.json` から作る木 | 試作 |
| 付箋ズーム | 2 次元配置の上に表札と意見を付箋で置き、寄るほど付箋が増える | `public_result.json` から作る付箋の配置 | 試作 |
| 階層リスト（ツリー表示） | 上位・下位のクラスタを展開して個々の意見と出典まで辿る | `public_result.json` のみ | 本体の公開ビューアの「詳細モード」に入った（[ビューの選び方](../user-guide/view-gallery.md#hierarchy-list)） |
| 対立軸ビュー（DivCon） | [DivCon](#divcon) を広聴AI のまとまりに当て、対立軸ごとに左右の意見を並べる | `public_result.json` ＋ LLM で作る対立軸と採点 | 実験 |
| 賛否スライダー | [センチメント次元の付与](#sentiment-dimension)を広聴AI の出力に当て、重みのスライダーで賛成と反対が離れていく様子を見る | 賛否スコア（`stance_score`）つきの `public_result.json` ＋埋め込み | 実験 |
| 自分の声を探す | 自分の書いたことに近い意見と、それが多いまとまりを探す（参加者向け） | `public_result.json` のみ | 試作 |
| 要約から落ちた声 | 似た意見がほとんど無い声を、まとまりごとに孤立度の順に並べる | `public_result.json` から作る孤立度（埋め込みも使う） | 試作 |
| 一緒に言われた話題 | 同じ投稿の中で一緒に書かれた話題の組を、散布図の上で線で結ぶ | `public_result.json` から作る組 | 試作 |
| 話題の流れ | 意見の日時で区切り、話題の割合の移り変わりを描く | 日時の属性（ISO 8601）を持つ `public_result.json` | 試作 |

題材はチームみらい 2025「しゃべれるマニフェスト」の意見 21,348 件（[公開データセット](https://huggingface.co/datasets/nishiohirokazu/team-mirai-2025-embeddings)、CC BY 4.0）です。対立軸ビューと賛否スライダーは、そのうち賛否の割れそうな 4 つのまとまり（エネルギー・家族・移民・皇位継承）の 2,167 件だけを使っています。

- カタログ: <https://nishio.github.io/broadlistening-visualizations/>
- repo: <https://github.com/nishio/broadlistening-visualizations>（MIT License、最終 push 2026-11-11）

### 本体との関係

階層リストは本体の公開ビューアに入りました。ほかは本体に入れるかを判断していません。別のレポートに当てるには、表の「入力」にある追加の入力を、カタログの repo の README の「作り方」の手順でそのレポートから作り直します。対立軸ビューは軸と採点、話題の流れは日時の属性が要り、どちらも今の `public_result.json` の契約には含まれません。自分の可視化を試すときの出発点としても使えます。

## 本体に入れるとき

ここに載っている手法を本体に入れる場合は、Web UI ではなく **CLI の任意ステップまたは分析モードから**入れます（[CLI クイックスタート](../user-guide/cli-quickstart.md)）。既定では無効にし、結果は既存の仕組み（`arguments[].attributes` の属性、または分析モードごとの結果 JSON）に載せます。Web UI に載せるかは、CLI で結果を貯めて読み比べてから判断します。
